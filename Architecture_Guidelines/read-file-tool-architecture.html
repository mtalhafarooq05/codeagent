Local Code Agent · Architecture Guideline

read_file tool

A complete architectural view of how the local model discovers, requests, executes, and consumes a guarded file read. The emphasis is component responsibility and data flow; path-resolution mechanics are intentionally summarized.

Runtime: Node.js + TypeScript Model provider: Ollama Default model: qwen3:8b Capability: read-only

1. Purpose and boundary

read_file gives the model controlled access to project text files. It is not a general filesystem API and it does not make the model autonomous.

What it does

Reads a project-relative UTF-8 file, optionally restricted to an inclusive line range.

What it returns

Structured content, line metadata, total line count, truncation state, and a continuation line when needed.

What it cannot do

It cannot write, delete, rename, execute, install, use Git, or read arbitrary paths outside the project.

Core boundary: the model proposes a call, but application code owns validation, authorization, execution, limits, error handling, and the returned data.

2. Component architecture

The feature is split by responsibility. No provider-specific Ollama shape leaks into the tool, and no filesystem logic lives in the conversation loop.

3. End-to-end sequence

A file is never read simply because the user mentioned it. The model must emit a typed tool call, and the application must approve it through every boundary below.

Truthfulness safeguard: model text received alongside a tool request is buffered and not displayed. Only a later response with no tool request is emitted as the final answer.

4. Contracts and payloads

Tool definition exposed to the model

ToolRegistry.descriptors() strips execution code and exposes only a name, description, and JSON-schema-like input definition. The Ollama adapter converts this to a function tool. 

{
  "type": "function",
  "function": {
    "name": "read_file",
    "description": "Read a bounded range of lines from a text file inside the project.",
    "parameters": {
      "type": "object",
      "additionalProperties": false,
      "required": ["path"],
      "properties": {
        "path": { "type": "string" },
        "startLine": { "type": "integer", "minimum": 1 },
        "endLine": { "type": "integer", "minimum": 1 }
      }
    }
  }
}

Provider-neutral call

{
  "name": "read_file",
  "arguments": {
    "path": "src/session.ts",
    "startLine": 1,
    "endLine": 80
  }
}

Successful result

{
  "ok": true,
  "value": {
    "path": "src/session.ts",
    "content": "...",
    "startLine": 1,
    "endLine": 80,
    "totalLines": 112,
    "truncated": false
  }
}

Truncated result

{
  "ok": true,
  "value": {
    "path": "src/large-file.ts",
    "content": "...bounded content...",
    "startLine": 1,
    "endLine": 200,
    "totalLines": 870,
    "truncated": true,
    "nextStartLine": 201
  }
}

If the 32,000-character cap cuts through a line, nextStartLine points to that partially returned line. Re-reading it may duplicate some text, but it does not skip unseen content.

Failure result

{
  "ok": false,
  "error": {
    "code": "SENSITIVE_FILE",
    "message": "Reading likely secret files is not allowed."
  }
}

Expected tool failures are data, not thrown exceptions. This lets the model explain the limitation or choose a safer follow-up. Unexpected failures are contained by the registry.

5. Tool execution pipeline

  1. Cancellation check. Stop immediately if the user already cancelled the request.
  2. Argument parsing. Require an object, allow only path, startLine, and endLine, and validate positive integer ranges.
  3. Sensitive-name policy. Reject common secret and private-key names before opening anything.
  4. Safe project open. Ask openProjectFile for one validated file handle tied to the selected project.
  5. File-kind and size check. Require a regular file and reject a reported size above 1 MiB.
  6. Bounded read. Read from the same handle in 64 KiB chunks into a buffer capped at 1 MiB + 1 byte. The extra byte detects growth after the initial size check.
  7. Text validation. Reject NUL-containing data, invalid UTF-8, and control-heavy content.
  8. Line processing. Normalize CRLF, calculate total lines, validate startLine, and select the requested inclusive range.
  9. Output bounds. Return no more than 200 lines or 32,000 characters and calculate continuation metadata.
  10. Cleanup. Close the file handle in a finally block on every result path.
Why both size checks? A file can change between metadata inspection and reading. The first check avoids unnecessary work; the bounded buffer prevents a growing file from exceeding the enforced limit.

7. Limits and cancellation

LimitCurrent valueArchitectural reason
File bytes1 MiBBounds memory and prevents large assets from entering model context.
Read chunk64 KiBCreates regular cancellation checkpoints during I/O.
Returned lines200Keeps one call focused and makes pagination predictable.
Returned characters32,000Protects the context window from very long lines or dense files.
Tool calls per model response4Stops one response from scheduling an arbitrary batch of reads.
Total tool calls per user request8Bounds accumulated context and filesystem work.
Tool rounds8Prevents an endless model → tool → model loop.

Cancellation propagation

The CLI creates one AbortController per user request. Its signal is passed through ChatSession → ModelProvider and ToolRegistry → read_file → bounded file reads. The provider also converts abort into OllamaClient.abort().

Checks occur before a model round, before each queued tool call, at registry entry, before/after safe opening, and between file chunks. This prevents later queued reads from running after Ctrl+C.

Expected tool errors are serialized into the next model request. This means the model can say “that file is blocked” without the entire chat session crashing.

9. Security model and residual risk

Enforced boundaries

  • Project-relative paths only.
  • No traversal outside the selected project.
  • No symbolic links or junction traversal.
  • One validated handle is used for the actual read.
  • Common secret-file names are denied.
  • Strict UTF-8 and binary-content checks.
  • File, output, call, and round limits.
  • No write or command capability is registered.

Trust boundaries

  • User input is untrusted.
  • Model-produced arguments are untrusted.
  • Provider chunks are runtime-validated.
  • Project paths and file metadata may change during a request.
  • File contents are untrusted data and may contain prompt-injection text.
  • The process still inherits the operating-system permissions of the user running it.

11. Extension guidelines

Future tools should follow the same boundaries rather than adding special cases to the session or provider.

  1. Implement Tool. Give the capability one exact name, a concise description, an explicit input schema, and an execute method.
  2. Keep policy inside the capability. The registry dispatches; it should not learn file-specific or command-specific rules.
  3. Reuse focused utilities. Cross-cutting mechanics such as project-path handling belong in named utility modules, not a catch-all helper file.
  4. Return structured expected errors. Do not throw for ordinary invalid input or denied policy decisions.
  5. Accept and check AbortSignal. Long work must provide cancellation checkpoints.
  6. Bound resource use. Define output, time, call, or byte limits appropriate to the new capability.
  7. Register explicitly. Add the tool in createProjectToolRegistry(); registration is the capability allowlist.
  8. Test each boundary. Cover the tool alone, registry dispatch, session round trip, and provider schema only where the shared contract changes.
Important: write or command tools have a fundamentally higher risk than read_file. They need their own approval, sandboxing, scope, and recovery design; they should not inherit “safe” status merely because they use the same registry.

Why the design is provider-swappable

ChatSession consumes only ModelProvider, ChatMessage, ModelStreamEvent, and neutral tool contracts. A future ChatGPT or Gemini provider should translate those neutral types to its API exactly as OllamaProvider does. The registry and read_file should not need to change.
